# Webshell: виконання коду на сервері

## Що таке PHAR і чому це небезпечно

PHAR — це PHP-аналог ZIP для бібліотек. У нього є особливість:
коли PHP **будь-якою функцією** звертається до файлу через `phar://`,
він автоматично десеріалізує метадані архіву.

is_file('phar://upload/file.png')
↓
PHP читає метадані PHAR
↓
автоматичний unserialize()
↓
запускається PHP-код із метаданих


Не `eval()`. Не `include()`. Просто перевірка чи існує файл — і вже RCE.

## PHAR-поліглот: файл-обманка

Завантажили файл `attachment_xlsx.png`:
- Перші байти — справжній PNG-заголовок → проходить перевірку типу
- Всередині — PHAR-архів із PHP-гаджетом у метаданих

[PNG magic bytes] [PHAR metadata з PHP об'єктом]
↑ ↑
перевірка типу ОК код для виконання


---

## Gadget Chain: як PHP "сам" виконує код

PHP при десеріалізації автоматично викликає методи `__wakeup()` і `__destruct()`.
У SuiteCRM є класи, чиї такі методи при певній послідовності викликів
врешті доходять до `system()`.

Це не баг у конкретному методі — це ланцюжок легітимних методів,
який у сумі дає виконання команди.

## WAF Bypass: 200 КБ сміття

Cloudflare WAF блокував `phar://` у тілі запиту.
Але WAF перевіряє тільки перші ~180 КБ тіла (інакше він уповільнює все).

[0 ─────── 180 КБ] ← WAF перевіряє: тут тільки 'AAAA...'
[181 КБ ── кінець] ← тут phar:// → WAF не бачить


Додали 200 КБ символів 'A' перед payload — і запит пройшов.

GET /upload/shell.php?z=aWQ=   # base64('id')
