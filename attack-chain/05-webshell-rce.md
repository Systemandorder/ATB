# Webshell: виконання коду на сервері

## Серіалізація і десеріалізація  основа атаки

PHP вміє перетворювати об'єкт у рядок щоб зберегти або передати — це серіалізація.
Зворотнє — це десеріалізація: рядок знову стає об'єктом.

Небезпека в тому, що при десеріалізації PHP **автоматично викликає** магічні методи
класу — `__wakeup()` і `__destruct()`. Без питань, просто тому що так влаштована мова.
Зловмисник формує рядок так, щоб у цих методах виконалась його команда.

---

## Що таке PHAR і де тут проблема

PHAR — це архів для PHP-бібліотек, як ZIP але для PHP-коду.
Всередині архіву є метадані  і вони зберігаються у серіалізованому вигляді.

Ключова особливість: якщо будь-яка PHP-функція отримує шлях виду `phar://...`,
вона автоматично десеріалізує метадані цього архіву.

Навіть `is_file()` — яка просто перевіряє чи існує файл:

is_file('phar://uploads/photo.png')
→ PHP відкриває архів
→ десеріалізує метадані
→ автоматично викликає __wakeup() або __destruct()
→ виконується код зловмисника


`include` або `eval` — всі знають що небезпечні, їх фільтрують.
А `is_file` — здається нешкідливим. SuiteCRM робить `is_file($importFile)` десь у коді
для перевірки завантаженого файлу  і цього вже достатньо.

## Файл-обманка (PHAR-поліглот)

Завантажили файл з назвою `attachment_xlsx.png`.
Він одночасно є двома речами:

Перші байти файлу — справжній PNG-заголовок. Перевірка типу бачить PNG і пропускає.
Далі всередині — PHAR-архів з серіалізованим PHP-об'єктом у метаданих.

Завантажувач перевірив розширення і MIME — все ОК, це "картинка".
Але коли сервер звернувся до файлу через `phar://` — спрацювала десеріалізація.

## Gadget chain — ланцюжок звичайного коду

У SuiteCRM багато PHP-класів з методами `__destruct()` і `__wakeup()`.
Самі по собі — нормальний робочий код. Але вони викликають один одного:

метод класу A → викликає метод класу B → викликає метод класу C → врешті `system()`

Зловмисник формує серіалізований об'єкт так, щоб у фінальний `system()` потрапила
його команда. PHP сам проходить весь ланцюжок — просто десеріалізуючи метадані PHAR.
Жодного окремого бага в кожному методі — небезпечна лише їхня сукупність.

## WAF Bypass — 200 КБ сміття

Cloudflare WAF блокував рядок `phar://` у тілі запиту.
Але WAF фізично не може перевіряти нескінченно великі запити — він сканує
тільки перші ~180 КБ тіла, далі просто пропускає.

Перед payload додали 200 КБ символів 'A'. WAF перевірив перші 180 КБ —
побачив тільки 'AAAA...', нічого підозрілого. Далі не дивився.
PHP обробив запит повністю і знайшов `phar://` після сміття.

## Результат

Отримали веб-шел — файл на сервері, через який можна виконувати команди.
Запустили `id` щоб перевірити від якого користувача працює сервер:

```bash
GET /upload/shell.php?z=aWQ=   # aWQ= це base64 від 'id'
→ uid=993(nginx)
```

Тепер будь-яка команда на сервері — через звичайний HTTP-запит.
