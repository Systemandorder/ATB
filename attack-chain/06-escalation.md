#  Ескалація привілеїв

## Загальна схема

Після webshell мали доступ від імені nginx на одному сервері.
Ціль  root скрізь. Ось як ланцюжок розгортався далі:

nginx (один сервер)
→ Grafana — той самий пароль що і від Moodle
→ Zabbix БД — Grafana мала право писати туди
→ Zabbix адмін — підроблена cookie через вкрадений ключ
→ root на 33 000 серверах — Zabbix керує всіма
→ SSH-ключ у бекапі — відкрив усе інше


---

## Крок 1 — Grafana: один пароль у двох місцях

Пароль від корпоративної пошти знайшли раніше через Moodle.
Той самий пароль підійшов до Grafana — системи моніторингу.

Це credential reuse: одна людина або система використовує однаковий пароль
у кількох місцях. Витік одного пароля -це доступ до всього де він повторюється.

---

## Крок 2 — Grafana пише в Zabbix БД

Grafana підключена до бази даних Zabbix щоб читати метрики для графіків.
Але підключення було з правами на запис і цього ніхто не обмежив.

Через Grafana API можна виконувати довільний SQL. Вставили рядок напряму
в таблицю сесій Zabbix — це  фейковий запис адміністратора з вигаданим session ID.

---

## Крок 3 — Підробка cookie Zabbix

Zabbix не довіряє session ID сліпо,бо  він підписує cookie через HMAC-SHA256.
HMAC — це криптографічний підпис, без секретного ключа підробити неможливо.

Але секретний ключ `session_key` лежав у конфіг-файлі на сервері.
Той самий сервер вже читали через LFI на кроці 4.

Маючи ключ, підписали свій фейковий session ID точно так само як це робить Zabbix.
Система прийняла підроблену cookie як справжню і видала права адміна.

---

## Крок 4 — Zabbix адмін = root на 33 000 серверах

Zabbix —  це система моніторингу. Вона запускає перевірки і скрипти на всіх серверах мережі.
Агент Zabbix на кожному сервері працює від root, щоб мати доступ до всіх метрик системи.

Через Zabbix API адмін може створити скрипт і запустити його на будь-якому хості.
Запустили `id`  у відповідь `uid=0(root)`. Далі через SSH key-trust між серверами
(коли сервери довіряють одне одному без пароля) отримали root і на вебсервері.

Компрометація Zabbix автоматично означає компрометацію всього що він моніторить.

---

## Крок 5 — SSH-ключ у бекапі

Jenkins — це сервер збірки і деплою  мав підключену мережеву папку з бекапами.
Всередині лежав щоденний архів bastion-хоста  головного сервера входу в мережу.

Розпакували архів і знайшли приватний SSH-ключ адміністратора всієї мережі.
Один файл відкрив root-доступ до GitLab, Jenkins, Harbor, CI/CD і Zabbix-сервера.

---

## Чому весь ланцюжок спрацював

Кожна окрема вразливість не була катастрофою сама по собі.
Але кожен крок давав те, що потрібно для наступного:

| Що отримали | Що це відкрило |
|---|---|
| Пароль від Moodle | Вхід у Grafana |
| Grafana з write-доступом | Фейкова сесія в Zabbix БД |
| session_key через LFI | Підпис фейкової cookie |
| Zabbix адмін | Root на всіх серверах |
| Root на Jenkins | Бекап з SSH-ключем |
| SSH-ключ | Весь GitLab, CI/CD, інфраструктура |

Це lateral movement — це  горизонтальне переміщення по мережі,
де кожен наступний крок використовує здобуток попереднього.
