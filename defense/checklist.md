# Defense Checklist

## Mobile / API
- [ ] Ніяких секретів в APK — логіни, паролі, токени не повинні бути в коді додатку,
      бо APK може завантажити і розпакувати будь-хто
- [ ] Static analysis у CI: `gitleaks`, `MobSF`, `apkleaks`  автоматична перевірка
      коду на секрети при кожному коміті, до того як потрапить у продакшн
- [ ] Ротація API credentials при релізі  навіть якщо старий пароль витік,
      він вже не працює
- [ ] Certificate Pinning  додаток приймає відповіді тільки від конкретного сертифіката,
      щоб не можна було перехопити трафік через підставний сервер

## Web Application
- [ ] Параметризовані запити для всього SQL включно з ключами масивів 
      дані ніколи не вставляються напряму в SQL-рядок
- [ ] Whitelist допустимих filter/sort значень  якщо в URL очікується число 490,
      приймати тільки конкретний список чисел, все інше це помилка
- [ ] Всі AJAX-ендпоінти вимагають авторизацію  анонімний запит не повинен
      отримувати жодних даних, навіть нешкідливих
- [ ] API не повертає конфіг-об'єкти  відповідь містить тільки потрібні поля,
      ніяких $CFG, ніяких системних шляхів, ніяких версій ПО
- [ ] `realpath()` + перевірка межі папки для file input —  це переконатись що файл
      знаходиться в дозволеній папці, а не десь в /etc через ../../../
- [ ] Валідація файлів: розширення + магічні байти — це перевіряти не тільки назву файлу
      але й перші байти вмісту, бо PNG можна назвати .php
- [ ] `phar://` wrapper відключений  PHP не буде автоматично десеріалізувати
      метадані архівів, навіть якщо хтось передасть phar:// шлях
- [ ] `unserialize()` з whitelist або замінити на JSON  обмежити які класи PHP
      може відтворити при десеріалізації, або взагалі не використовувати serialize
- [ ] Upload-директорія: заборона виконання PHP навіть якщо хтось завантажить
      PHP-файл, сервер поверне його як текст, а не виконає

## Auth & Access
- [ ] B2B реєстрація — ручна модерація. Новий постачальник не отримує доступ
      автоматично, адмін підтверджує кожен акаунт вручну
- [ ] Password reset: TTL 15 хв, одноразовий, rate limit — це посилання для скидання
      пароля живе 15 хвилин, після використання стає недійсним, не можна
      генерувати сотні таких посилань підряд
- [ ] MFA для Grafana, Zabbix, Jenkins, GitLab  навіть якщо пароль витік,
      без другого фактора зайти не можна
- [ ] Унікальні паролі для для кожної системи.Витік одного не відкриває всі інші

## Infrastructure
- [ ] Мережева сегментація: web → app → db і  веб-сервер не може напряму
      підключитись до бази даних, тільки через app-сервер
- [ ] B2B портали тільки через VPN або IP whitelist зовнішній зловмисник
      взагалі не бачить сторінку реєстрації
- [ ] Grafana / Zabbix — read-only доступ до БД — система моніторингу читає метрики,
      але не може нічого записати в таблиці
- [ ] Zabbix agent не від root, `system.run` заборонений — це компрометація Zabbix
      не дає автоматично root на всіх серверах
- [ ] SSH key-trust між серверами  заборонений і сервер A не може зайти на сервер B
      без пароля або окремого підтвердження

## Secrets
- [ ] Секрети у Vault, не в PHP-конфігах.Паролі зберігаються в окремій захищеній
      системі (HashiCorp Vault, AWS Secrets Manager), а не в config.php поруч з кодом
- [ ] Конфіги поза web root. config.php недоступний через браузер навіть якщо
      хтось знає його шлях
- [ ] Змінити всі дефолтні паролі — Splunk, Grafana, Jenkins при встановленні мають
      дефолтні паролі типу admin/changeme, їх треба змінити до першого запуску

## Backups
- [ ] Бекапи зашифровані  навіть якщо хтось дістанеться до файлу архіву,
      без ключа шифрування він нічого не прочитає
- [ ] `.ssh` виключено з архівів  приватні SSH-ключі не потрапляють у бекап,
      щоб через бекап не отримати доступ до всієї мережі
- [ ] CIFS-шара доступна тільки з backup-сервера  підключитись до папки з бекапами
      може лише виділений сервер, не будь-який хост у мережі

## Monitoring
- [ ] Алерти на масові помилки auth  якщо хтось перебирає паролі,
      SIEM помічає сотні невдалих спроб і сповіщає команду
- [ ] Алерти на нові `script.create` у Zabbix  створення нового скрипта в Zabbix
      є рідкісною подією, кожна така дія повинна одразу привертати увагу
- [ ] Алерти на нові адмін-сесії— якщо з'явилась нова адмін-сесія в Zabbix або GitLab
      в незвичний час або з незнайомого IP одразу сповіщення
- [ ] Penetration testing раз на рік  запрошена команда намагається зламати систему
      контрольовано, щоб знайти проблеми до реальних зловмисників
